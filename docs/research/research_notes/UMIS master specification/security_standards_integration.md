# UMIS: Access Control, Auditing, Interoperability Standards and Integration Patterns

Scope: (1) the role and permission model, (2) audit and security requirements, (3) the integration standards and API patterns UMIS should support. Target stack: Laravel 13 + PostgreSQL 16 + Inertia/Vue 3, for a Philippine HEI (Data Privacy Act of 2012 / NPC applies). Researched November 2026.

Source note: I ran about 15 search/fetch calls. Vendor items (Banner, PeopleSoft, Workday, 1EdTech, Moodle, OWASP, NPC) come from search results that point at primary documentation. A few items are tagged "[ref, not fetched]": these are canonical references (IETF RFCs, Stripe docs, the OpenAPI spec) cited from prior knowledge and not re-checked in this session. Treat them as lower-confidence citations.

## Q1. Role and permission model (RBAC vs ABAC, scoping, SoD, delegation, field-level sensitivity; how Banner, PeopleSoft and Workday do it)

### Takeaway
All three major SIS/ERP vendors use the same layered design. Coarse **functional permissions** (which pages, tasks or actions) are granted through named groups or classes. A separate **data-scope layer** (row-level security by institution, campus, career, program or department) narrows which records those permissions apply to. **Workflow or business-process security** then governs who may initiate or approve, which is where separation of duties is enforced. UMIS should copy this: scoped RBAC as the base, plus ABAC-style policy checks for record ownership, sensitivity and SoD, with PostgreSQL RLS as a defence-in-depth backstop.

### Cited Findings
**Ellucian Banner**
- Banner never grants a user direct access to a single admin page or table. Privileges are granted to an Oracle username in groups called **security classes** (or roles). — [Drake University Banner Security FAQ](https://drake.teamdynamix.com/TDClient/2025/Portal/KB/ArticleDet?ID=146902)
- **Fine-Grained Access Control (FGAC)** gives row-level security based on existing Banner columns and tables. It is built on Oracle (VPD) functionality. At query time the GOKFGAC package reads the security policy and appends predicates to the user's SQL. **Value-Based Security (VBS)** in Banner 7 replaced the older module-specific General/Student/Financial Aid VBS. — [Sungard/FHDA VBS overview deck](https://fhdafiles.fhda.edu/downloads/eisDocs/ValueBasedSecurityOverviewPP.pdf)
- To control the editing scope on a given Banner page, an FGAC "cognate" (a business-profile-like predicate group) is paired with the user's security class. — [Tulane: Identify class-FGAC pairings](https://tulaneu.atlassian.net/wiki/x/IQAvJ)
- Reference handbooks: [Banner General Security Administration Handbook (Mar 2020)](https://webspace.potsdam.edu/groups/ais/banner/guides/Banner_General_Security_Administration_Handbook_March_2020.pdf); [Banner General Data Security Handbook 8.6.3](https://banadmin.jefferson.edu/Banner_Docs/OtherDocs/Banner%20General%20Data%20Security%20Handbook%208.6.3.pdf). Caveat: these are Banner 7/8-era sources. I found no current Banner 9 / Ethos security reference.

**Oracle PeopleSoft Campus Solutions**
- Academic-structure security has layered components: Academic Institution Security, Institution/Campus, Institution/Career, Academic Program and Academic Plan. Oracle recommends securing institution alone and also combined with campus/career, because not every page is keyed by all of them. — [Oracle CS 9.2: Securing Academic Structure](https://docs.oracle.com/en/applications/peoplesoft/campus-solutions/9.2.038/campus-solutions-application-fundamentals/securing-academic-structure.html)
- Secure views restrict student data per user ID by institution, campus, career, program and plan. — [Oracle CS: Understanding Row-Level Security](https://docs.oracle.com/en/applications/peoplesoft/campus-solutions/9.2.038/campus-solutions-application-fundamentals/understanding-row-level-security.html)
- Department (tree-based) data access is granted only to **row-security permission lists**, for example limited to Parking and Student Life departments. Row-level security cannot be built by combining roles: a user has exactly one row-security role/permission list. — [Oracle CS: Managing Department Security](https://docs.oracle.com/cd/G11181_01/cs92pbr35/eng/cs/lsfn/ManagingDepartmentSecurity.html)
- Functional access uses **permission lists → roles → user profiles** (the standard PeopleSoft model). — [Oracle: Understanding PeopleSoft Security](https://docs.oracle.com/cd/G40410_01/hcm92pbr53/eng/hcm/hhaf/UnderstandingPeopleSoftSecurity-e32979.html)
- Auditing row-level grants is a known pain point. Admins write SQL across separate Institution and Career row-security tables to list one user's scope. — [Oracle MOSC thread](https://community.oracle.com/mosc/discussion/4558683/sql-to-return-all-row-level-security-assigned-to-an-oprid)

**Workday (incl. Workday Student)**
- A **security group** is a collection of users used to grant access. Types include user-based, role-based (assigned on an organization, e.g. a department or program) and rule-based groups. — [Workday Configurable Security Framework](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/configurable-security-framework.html); [Workday rule-based security](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/rule-based-security.html)
- **Domain security policies** decide which groups can access the securable items (reports, tasks, data sources) in a functional domain, with *View* or *View and Modify* permission. — [Workday security policy configuration](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-policy-configuration-and-activation.html)
- **Business process security policies** grant groups the right to initiate, rescind, approve and so on for a process type. Workflow steps route to **security groups, not individuals**. — [same](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-policy-configuration-and-activation.html)
- Policy changes stay pending until an "Activate Pending Security Policy Changes" task runs, so security config is itself versioned and change-controlled. Admins are told to audit before removing groups, because that can break routings. — [same](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-policy-configuration-and-activation.html)
- Workday Student uses the same configurable security framework. — [Workday Student for Administrators: configurable security overview](https://doc.workday.com/workday-education/en-us/course-manuals/student-for-administrators/configurable-security-overview.html)

**Laravel mapping**
- spatie/laravel-permission has an optional **teams** feature that scopes role and permission assignments by a `team_id` foreign key. The column name is configurable (e.g. `branch_id`). The feature must be enabled before the initial migration. The active team is set per request with `setPermissionsTeamId()`, typically in middleware. Docs exist for v5 through v8. — [Spatie docs: Teams permissions](https://spatie.be/docs/laravel-permission/v6/basic-usage/teams-permissions); [v8](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions)
- Practitioners report limits when team mode is used as full multi-tenancy, e.g. global "root" roles across teams. — [GitHub discussion #2657](https://www.github.com/spatie/laravel-permission/discussions/2657); [DEV: moving away from Spatie team mode](https://dev.to/filamentmastery/why-i-moved-away-from-spaties-team-mode-for-multi-tenancy-3g8h)

### Inferences
- **Recommended UMIS model: scoped RBAC + policy (ABAC) layer**
  1. *Permissions* are fine-grained verbs on resources (`grades.encode`, `grades.approve`, `grades.change_after_finalize`, `payments.post`, `refunds.approve`, `student.health.view`). These are equivalent to Banner security-class objects, PeopleSoft permission lists and Workday domains.
  2. *Roles* are bundles of permissions (Registrar Staff, Dean, Department Chair, Faculty, Cashier, Bursar, Guidance Counselor, Clinic Nurse, Student, Parent/Guardian, Auditor, Sysadmin).
  3. *Role assignment carries a scope*: `(user, role, scope_type, scope_id, valid_from, valid_to, granted_by, reason)`, where scope_type ∈ {university, campus, college, department, program, section/class, self}. This mirrors PeopleSoft institution/campus/career/program/plan and Workday role-based groups on organizations. Spatie's single `team_id` covers one scope dimension. For a campus → college → department → program hierarchy, either (a) set the "team" to an org-unit id and resolve inheritance with a closure table or `ltree` of org units, or (b) keep Spatie for permission bundles and use a custom `role_assignments` table with scope plus validity dates. Option (b) is more flexible and matches the vendors better.
  4. *Policies* (Laravel Gates/Policies) evaluate attributes: the actor's scopes contain the record's org unit; the faculty member teaches the section; the student is the subject (`self`); the record's sensitivity class; the term is open; the actor is not the encoder (SoD).
- **Hierarchy**: scope inheritance goes downward (a college-scoped Dean sees all its departments and programs). Avoid deep role-inheritance trees and prefer flat roles with composite bundles, since vendor experience (PeopleSoft's single row-security role) shows inherited data scopes are hard to audit.
- **Separation of duties** should be enforced as Workday-style workflow steps with actor ≠ initiator checks:
  - Grade lifecycle: faculty encodes → chair/dean approves → registrar finalizes. Any post-finalization change needs a change request with a reason code, approved by someone other than the requester, with the before/after values logged.
  - Finance: cashier posts receipts, a separate approver approves refunds, voids and write-offs. Static SoD conflicts (role pairs that cannot be held together in the same scope, e.g. Cashier + Refund Approver) are checked at assignment time. Dynamic SoD is checked at action time.
  - Security admin: whoever grants roles cannot grant to themselves, and high-privilege grants need a second approver (mirrors Workday's pending/activate model).
- **Delegation and temporary access**: delegations are time-boxed role assignments (`valid_to`) with `delegated_by` and auto-expiry (scheduled job plus checks at evaluation time). Delegation of SoD-conflicting permissions is not allowed. Break-glass access is a special role that requires a reason, alerts the DPO/security team and expires quickly (e.g. 4 h).
- **Impersonation** ("view as"): only for support and Sysadmin roles, read-only by default, a banner shown in the UI, every request tagged with both `actor_id` and `impersonated_user_id` in the audit log, a mandatory reason, and never allowed for users with higher privilege.
- **Field-level sensitivity**: classify columns (Public / Internal / Confidential / Sensitive Personal Information under DPA s.3(l): health, government IDs, disciplinary, financial). Enforce through (a) API Resource/Inertia prop serializers that drop fields unless the actor holds `*.view_sensitive`, (b) separate tables for health, discipline and counseling records with their own policies, and (c) audit logging of every read of sensitive records (read-access logging, not just writes).
- **PostgreSQL RLS** as a backstop: set `SET LOCAL app.user_id / app.scopes` per transaction from Laravel middleware and define RLS policies on high-sensitivity tables (grades, health, discipline, student_accounts). This is the equivalent of Banner FGAC/Oracle VPD. The app must connect as a non-owner role (RLS is bypassed by table owners unless `FORCE ROW LEVEL SECURITY`). Watch for connection pooling (PgBouncer transaction mode needs `SET LOCAL` inside the transaction).
- Provide an **access review report** (who has what, in which scope, granted by whom, expiring when). The PeopleSoft MOSC thread shows this is otherwise painful, and NPC compliance expects periodic access review.

### Gaps
- No current (Banner 9 / Ethos, 2024–2026) Ellucian security documentation surfaced. Banner facts are from Banner 7/8-era materials.
- I did not verify whether spatie/laravel-permission v7/v8 adds native hierarchical teams or wildcard scopes.
- I found no published SoD conflict matrix specific to HEIs. The examples above are inferred from the vendor workflow models.

## Q2. Audit trail and application security requirements (ASVS level, MFA, sessions, encryption, backups, retention; Philippine NPC)

### Takeaway
UMIS should target **OWASP ASVS 5.0 Level 2** across the board, with Level 3 controls for authentication, authorization, audit and crypto on grade, financial and sensitive-personal-information modules. **NPC Circular 2023-06** (in force 30 March 2024; compliance deadline 30 March 2025) is the binding Philippine baseline for security controls. It applies to private and public HEIs alike. Audit should be an append-only, tamper-evident event log that captures who, what, when, where and before/after values. Grade and financial records should be immutable with compensating entries.

### Cited Findings
- OWASP ASVS **5.0.0 was released 30 May 2025** (Global AppSec EU Barcelona). It keeps three cumulative levels (L1–L3), rebalanced so L1 is easier to adopt, and grew to about 350 requirements across 17 chapters. New standalone chapters cover tokens/self-contained tokens, OAuth/OIDC and WebRTC. Requirements are cited as `v5.0.0-x.y.z`. — [OWASP ASVS GitHub](https://github.com/OWASP/ASVS); [Scott Helme: ASVS 5.0.0 is here](https://scotthelme.co.uk/owasp-asvs-5-0-0-is-here/); [SoftwareMill: what's new in ASVS 5.0](https://softwaremill.com/whats-new-in-asvs-5-0/). Exact counts differ slightly between secondary sources.
- **NPC Circular 2023-06** ("Security of Personal Data in the Government and the Private Sector") applies to all natural or juridical persons processing personal data in or outside the Philippines. It repealed NPC Circular 16-01, which was government-only. — [NPC announcement](https://privacy.gov.ph/?p=46138); [Digital Policy Alert](https://digitalpolicyalert.org/change/9243-national-privacy-commission-npc-circular-2023-06-on-security-of-personal-data-in-the-government-and-private-sector)
- It took effect 30 March 2024, and PICs/PIPs had until 30 March 2025 to comply. — [NPC](https://privacy.gov.ph/?p=46138); [Baker McKenzie](https://insightplus.bakermckenzie.com/bm/data-technology/philippines-minimum-requirements-for-security-of-personal-data-issued-by-the-national-privacy-commission). Adoption date is reported as 1 Dec 2023 by Digital Policy Alert. Thales gives an "issued 1 April 2024" date, which matches the NPC announcement date.
- Its requirements include a **privacy impact assessment (PIA) for every processing system** handling personal data, access only from authorized software and known, properly configured devices, and storage limited to the period necessary. — [NPC FAQ on Circular 2023-06](https://privacy.gov.ph/wp-content/uploads/2024/12/v12-19-2024_FAQ-NPC-Circular-2023-06_NNJ_JDN.pdf) (via search summary; direct fetch returned 403); [Thales compliance brief](https://cpl.thalesgroup.com/resources/compliance/npc-circular-2023-06-securing-personal-data-in-the-philippines-compliance-brief)
- Sanctions for non-compliance include compliance and enforcement orders, cease-and-desist orders, temporary or permanent processing bans, and fines. — [Thales](https://cpl.thalesgroup.com/compliance/apac/data-security-compliance-npc-circular-2023-06)
- The NPC FAQ says "high volume of data" is not defined and points to the registration criteria in NPC Circular 2022-04. — [NPC FAQ](https://privacy.gov.ph/wp-content/uploads/2024/12/v12-19-2024_FAQ-NPC-Circular-2023-06_NNJ_JDN.pdf)
- Workday treats security-policy changes as pending until explicitly activated. Security configuration is itself an audited, change-controlled artifact. — [Workday](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-policy-configuration-and-activation.html)

### Inferences
- **What to log** (one `audit_events` table, append-only):
  - `id` (ULID), `occurred_at` (timestamptz, DB clock), `actor_user_id`, `impersonator_user_id`, `actor_roles/scope snapshot`, `auth_method` (password+TOTP, SSO, API token/client_id), `ip`, `user_agent`, `request_id/correlation_id`
  - `action` (verb, e.g. `grade.changed`, `refund.approved`, `role.granted`, `record.viewed_sensitive`, `login.failed`, `export.generated`), `subject_type/subject_id`, `org_unit_id`
  - `before` / `after` JSONB diff, with sensitive values hashed or masked where appropriate
  - `reason_code` + free-text justification (mandatory for grade changes after finalization, refunds, voids, break-glass and impersonation)
  - `prev_hash` and `hash` (SHA-256 chain) for tamper evidence
- **Immutability in PostgreSQL**: the app DB role gets INSERT/SELECT only on audit tables. A trigger raises on UPDATE/DELETE. Partition monthly (`PARTITION BY RANGE (occurred_at)`), detach and archive old partitions to WORM object storage (S3 Object Lock or equivalent). Periodically anchor the latest hash externally (e.g. a signed daily digest emailed or stored off-system) so the DB owner cannot rewrite history undetected. Ship logs in near real time to a separate log store or SIEM.
- **Laravel**: use model observers or a package (e.g. owen-it/laravel-auditing or spatie/laravel-activitylog) for CRUD diffs. Domain events (`GradeFinalized`, `GradeChangeApproved`, `PaymentPosted`, `RefundApproved`) should write explicit audit entries inside the same DB transaction as the business change. CRUD-level diffs alone miss intent.
- **Grade audit**: grades are versioned rows (`grade_entries` append-only; the current grade is a view or the latest approved version). Store encoder, approver, finalizer and timestamps for each version. The Registrar can produce a full per-student and per-section grade-change history. Transcript generation reads only finalized versions.
- **Financial audit**: a double-entry, append-only ledger (`journal_entries` + `journal_lines`, Σdebit = Σcredit enforced by a deferred constraint trigger). No UPDATE or DELETE: corrections use reversing entries. Official receipt numbers come from gap-free sequences per cashier/collection point (BIR requirement — verify). Day-end cashier close is a locked batch. Every refund, void and discount links to an approval record.
- **Retention** (to be confirmed with counsel and CHED): academic records and transcripts are permanent. Financial books and records follow BIR retention, commonly cited as 10 years under the NIRC as amended (verify; RR 17-2013 / later amendments). Audit logs are kept at least as long as the records they protect for grades and finance, and 1–3 years for general access logs. The DPA principle requires deletion or anonymization of personal data that is no longer needed (e.g. unenrolled applicants) under a documented retention schedule.
- **Application security baseline** (ASVS 5.0 L2 mapped to Laravel):
  - *Auth*: MFA mandatory for all staff and faculty (TOTP/WebAuthn passkeys via Laravel Fortify 2FA or a WebAuthn package). Prefer institutional SSO (SAML/OIDC with Google Workspace or Microsoft Entra, which many PH HEIs use) with MFA enforced at the IdP. Students get MFA optional at first, required for financial actions. Use the Argon2id/bcrypt defaults and breached-password checks (`Password::uncompromised()`).
  - *Sessions*: server-side sessions (database/redis driver), `secure`, `httpOnly`, `SameSite=Lax`, idle timeout of 15–30 min for staff, absolute timeout of 8–12 h, session ID regenerated on login and privilege change, re-authentication for sensitive actions (grade finalization, refund approval, role grants), and a list of active sessions with "log out everywhere".
  - *Rate limiting*: Laravel `RateLimiter` on login, password reset, OTP and public endpoints; per-token limits on the API; account lockout with exponential backoff; alerts on credential stuffing.
  - *Encryption*: TLS 1.2+ (prefer 1.3) and HSTS. Encrypt at rest at the disk/volume level, plus application-level encryption (Laravel `encrypted` casts, AES-256-CBC/GCM with app key) for SPI columns such as government IDs (TIN, PhilHealth, SSS/GSIS, PhilSys), health notes and bank details. Use blind indexes (HMAC) where search is needed. Keep keys in a KMS or secret manager and keep an `APP_PREVIOUS_KEYS` rotation plan.
  - *Headers/CSP*: strict nonce-based CSP, no inline scripts, CSRF tokens (Sanctum SPA cookie mode for Inertia), output encoding through Vue's default escaping, and no `v-html` on user data.
  - *Backups*: encrypted, automated daily full backups plus PITR via WAL archiving (pgBackRest/WAL-G), off-site/immutable copies, quarterly restore drills, and documented RPO/RTO (e.g. RPO ≤ 15 min, RTO ≤ 4 h for the registrar and cashier systems).
  - *Archival*: move closed terms and alumni to archive partitions or read-only schemas. Keep transcripts reproducible from archived finalized data.
  - *Privacy ops (DPA/NPC)*: DPO appointment and NPC registration (where thresholds apply), a PIA per module, breach notification to the NPC and data subjects within 72 hours of knowledge (NPC Circular 16-03 — verify current), data-subject-rights workflows (access, correction, erasure where lawful, portability), consent and notice records, and data-sharing agreements for integrations (e.g. Moodle hosting, CHED, scholarship agencies).

## Q3. Interoperability standards and integration and API patterns (OneRoster, LTI, CLR/Open Badges, PESC, Ed-Fi, CASE, Moodle, REST best practice)

### Takeaway
Minimum viable interoperability for a Philippine university running Moodle:
- **(a)** Moodle sync. Either use Moodle's web services API (`core_user_*`, `core_course_*`, `enrol_manual_enrol_users`, grade read-back), or have UMIS act as a **OneRoster 1.2 Rostering provider** that Moodle's `enrol_oneroster` plugin consumes.
- **(b)** **LTI 1.3 / LTI Advantage** for launching UMIS views from Moodle, or Moodle activities from UMIS.
- **(c)** **Open Badges 3.0 / CLR 2.0** for verifiable credentials and digital diplomas or micro-credentials. This is now final and growing in importance.
- **(d)** **PESC transcript** export (XML; JSON-LD in progress) only if international or US transfer demand exists.
- **(e)** **CASE 1.1** if outcomes-based education (OBE, which CHED requires) competency frameworks need exchanging.

**Ed-Fi** is K-12/US-state focused and low priority. The UMIS API itself should be resource-oriented REST with an OpenAPI 3.1 contract, OAuth2 client-credentials scopes, cursor pagination, idempotency keys on payment endpoints and signed webhooks.

### Cited Findings
**1EdTech OneRoster 1.2**
- It defines three independently implementable services: **Rostering**, **Resources** and **Gradebook**, plus an Assessment Results Profile that extends Gradebook. Each has REST/JSON and CSV bindings, and conformance requires at least one service. — [1EdTech OneRoster 1.2 standard](https://standards.1edtech.org/oneroster/specifications/standards/v1p2); [1EdTech OneRoster page](https://www.1edtech.org/standards/oneroster)
- Rostering covers orgs, academic sessions, courses, classes, users and enrollments. — [Rostering Service IM](https://standards.1edtech.org/oneroster/specifications/standards/v1p2/services/rostering/im); [Rostering REST binding](https://standards.1edtech.org/oneroster/specifications/standards/v1p2/services/rostering/rest)
- Gradebook covers lineItems, results, categories and score scales, with both pull and push. The REST binding was issued 19 Sept 2022. — [Gradebook REST binding](https://www.imsglobal.org/sites/default/files/spec/oneroster/v1p2/gradebook-restbinding/OneRosterv1p2GradebookService_RESTBindv1p0.html); [Gradebook IM](https://standards.1edtech.org/oneroster/specifications/standards/v1p2/services/gradebook/im)
- Resources allocates resources to classes, courses and users but does not provide access to the resources. The binding includes OpenAPI files. — [Resources IM](https://standards.1edtech.org/oneroster/specifications/standards/v1p2/services/resources/im); [Resources REST binding](https://www.imsglobal.org/spec/oneroster/v1p2/resource/bind/rest)
- Overall it has about 22 CSV files and 81 REST endpoints (secondary source). — [Edlink: Everything about OneRoster 1.2](https://ed.link/community/everything-you-need-to-know-about-oneroster-1-2/)

**LTI 1.3 / LTI Advantage**
- LTI Advantage is LTI 1.3 core plus **Assignment and Grade Services (AGS) 2.0**, **Names and Role Provisioning Services (NRPS) 2.0** and **Deep Linking 2.0**. AGS lets a tool manage line items in the platform gradebook, including multiple grades per user per resource link. — [1EdTech LTI Advantage Implementation Guide](https://www.imsglobal.org/node/177591)
- Moodle can be an LTI 1.3 platform (consumer, via External tool) and also a tool (provider, via "Publish as LTI tool" with an LTI Advantage tab). When Moodle publishes as a tool, grades go back to the remote platform. In Moodle 5.0, grade and user sync runs asynchronously in scheduled tasks every 30 minutes by default. First-launch account provisioning is configurable per role (teacher default: "Existing and new accounts (prompt)"). — [Moodle docs 5.0: Publish as LTI tool](https://docs.moodle.org/500/en/Publish_as_LTI_tool); [Moodle 5.3 docs](https://docs.moodle.org/503/en/Publish_as_LTI_tool)

**Moodle enrolment and web services**
- Moodle's official **OneRoster enrolment plugin** (`enrol_oneroster`) is certified as a OneRoster 1.1 REST **Rostering consumer** and runs a scheduled sync task. Its listing mentions Gradebook consumer/provider and 1.2 support. Moodle HQ's intro slides list gradebook as a *future* plan, only manual auth and no course-category creation. Conflicting signals, so verify the current version. — [Moodle plugins: One Roster](https://moodle.org/plugins/enrol_oneroster); [Moodle HQ intro slides](https://docs.moodle.org:443/dev/images_dev/1/18/enrol_oneroster_intro.pdf)
- Moodle core web services (REST protocol with token auth) include `core_user_create_users` (required: username, email, lastname, etc.). Core user functions identify users by internal Moodle ID, which pushes integrators to keep an ID map (`idnumber`) or use upsert plugins. Enrolment uses `enrol_manual_enrol_users`, which needs the `enrol/manual:enrol` capability. — [DEV: Moodle web service APIs](https://dev.to/udarajayawardena/moodle-web-service-apis-51k4); [Moodle plugin: tool_userupsert](https://moodle.org/plugins/tool_userupsert); [Formswrite guide](https://formswrite.com/blog/moodle-api-create-users-courses-enrol-students)
- Sync-type enrolment plugins usually return false from `roles_protected`, so manual changes are not reverted on sync. This matters when mixing web-service enrolment and sync. — [Moodle dev docs: Enrolment plugins](https://docs.moodle.org/37/en/Development:Enrolment_plugins)

**Open Badges 3.0 / CLR 2.0**
- Open Badges 3.0 is a **Final Release**: the Certification Guide is dated 12 Dec 2025 and the Implementation Guide is final. It aligns with the **W3C Verifiable Credentials Data Model 2.0** (also compatible with VCDM 1.1). — [OB 3.0 Certification Guide](https://www.imsglobal.org/spec/ob/v3p0/cert/); [OB 3.0 spec](https://www.imsglobal.org/spec/ob/v3p0); [OB 3.0 Impl Guide](https://standards.1edtech.org/open-badges/guides/standards/v3p0/impl)
- A CLR 2.0 bundles many OB achievement credentials with associations between them. Each credential and the wrapping CLR are independently verifiable. — [CLR 2.0 Implementation Guide](https://www.imsglobal.org/spec/clr/v2p0/impl/)
- 1EdTech certification has issuer, displayer and host roles, and it requires features beyond the bare spec. — [OB 3.0 Certification Guide](https://www.imsglobal.org/spec/ob/v3p0/cert/)
- A PHP library implementing OB 3.0/CLR 2.0 exists (implementation example, not a standards source). — [Packagist: phil/open-badges](https://packagist.org/packages/phil/open-badges)

**UMIS API design (Laravel)**
- *Resources*: plural nouns, nested only one level (`/api/v1/students/{id}/enrollments`, `/api/v1/sections/{id}/roster`, `/api/v1/terms`, `/api/v1/invoices`, `/api/v1/payments`). Workflow transitions are explicit sub-resources or actions (`POST /grade-submissions/{id}/approve`), not PATCHes to status fields, so policies and SoD attach cleanly. Use stable public IDs (ULID/UUID), never sequential PKs. Student number is a natural key for lookup.
- *Versioning*: a URI major version (`/api/v1`) with additive changes within a version, deprecation through `Deprecation`/`Sunset` headers, and at least 12 months overlap. External standard APIs keep their own namespaces (`/ims/oneroster/...`, `/lti/...`).
- *Pagination*: cursor pagination (Laravel `cursorPaginate`) for large lists and sync feeds, plus `updated_since` filters for delta sync. Offset pagination is only for admin UIs. OneRoster endpoints must implement its own `limit/offset/filter/sort/fields` semantics.
- *Errors*: RFC 9457 `application/problem+json` with validation error arrays.
- *Idempotency*: required `Idempotency-Key` header on `POST /payments`, `/refunds` and `/enrollments`, plus payment-gateway callbacks. Store `(key, client_id, request_hash, response, status)` with a unique constraint and 24–72 h TTL, and replay the stored response. Gateway webhooks dedupe on provider event ID. All ledger postings are idempotent on a business key (e.g. gateway transaction reference).
- *Concurrency*: `ETag`/`If-Match` (or a version column) on mutable records such as grade sheets and student profiles to prevent lost updates.
- *Events/webhooks*: a transactional outbox table (written in the same DB transaction as the change, then dispatched by a queue worker) emitting domain events (`student.admitted`, `enrollment.created/dropped`, `section.created`, `grade.finalized`, `payment.posted`, `hold.placed/released`). Webhook subscriptions per client, HMAC-SHA256 signatures with timestamp (Standard Webhooks style), retries with exponential backoff, a dead-letter queue and a replay endpoint. Payloads are "thin" (id + type) for sensitive data, and consumers fetch details with scoped tokens.
- *Documentation*: OpenAPI 3.1 generated from code (e.g. `dedoc/scramble` for Laravel [ref, not fetched]), published to an internal developer portal, with contract tests in CI.
- *AuthN/AuthZ*:
  - **Sanctum** for the first-party Inertia SPA (cookie + CSRF) and simple personal tokens.
  - **Passport** (OAuth2 server) for third-party and machine clients: client-credentials grant for integrations (Moodle sync, OneRoster consumers, payment gateway) and authorization code + PKCE for user-delegated apps (e.g. a mobile app).
  - Scopes are coarse and resource-based (`roster:read`, `grades:read`, `grades:write`, `finance:read`, `payments:write`, `students.pii:read`, `oneroster.core.readonly`, the OneRoster-defined `https://purl.imsglobal.org/spec/or/v1p1/scope/roster-core.readonly` pattern). Each client is also bound to an org scope (e.g. only College of Engineering).
  - The token's scopes intersect with the client's service-account role, so an integration can never exceed its RBAC grant.
  - Short-lived access tokens (≤ 1 h), rotated client secrets or private_key_jwt, mTLS or IP allowlisting for high-risk clients, and all API calls written to the audit log with `client_id`.
- *Rate limiting*: per client and per route group (Laravel `RateLimiter::for('api', …)`), with `429` + `Retry-After`.
- *Data minimization*: field selection (`fields=`), with integrations given purpose-specific views (Moodle gets name, email, student number and enrolments, never financial or health data), documented in data-sharing agreements per the DPA.
