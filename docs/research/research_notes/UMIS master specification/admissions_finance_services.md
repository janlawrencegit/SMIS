# UMIS Non-Academic-Core Modules: Admissions, Finance, Services, HR, Library, Alumni, Portals (Philippines, 2026)

Scope note: research used ~16 web searches/fetches. Primary sources were reachable for ERPNext/Frappe Education, OpenEduCat, Koha, and some PH school fee sheets. Several PH regulatory figures could only be found in secondary legal commentaries (respicio.ph etc.) and conflict; these are flagged. Module-level feature/entity designs that are not directly sourced are given as **Inferences** (practitioner/domain knowledge), not as cited facts.

## 1. What entities and relationships does each module need, and how does it depend on the academic core?

### Takeaway
Every non-academic module hangs off a small set of academic-core anchors: Person -> Applicant -> Student, Program/Curriculum, Academic Year/Term (with PH exam periods prelim/midterm/finals), Section/Class Offering, and Enrollment (subjects + units). Assessment is a pure function of Enrollment x Fee Schedule (versioned per program/year level/term), and Clearance is an aggregation of "holds" raised by Library, Accounting, Clinic, Guidance/Discipline, Registrar, and department units. The open-source reference systems (ERPNext Education, OpenEduCat, Koha) confirm this layering.

### Cited Findings
**ERPNext / Frappe Education (fees)**
- Fee Structure is a template used to create fees/invoices; prerequisites are Academic Term, Academic Year, Program and Student Category; Company and Cost Center on it determine where ledger entries post — [Frappe docs: Fee Structure](https://docs.frappe.io/education/fee-structure); [ERPNext Fee Structure](https://docs.erpnext.com/docs/user/manual/en/fee-structure)
- Fee Schedule sets a payment timeline per Student Group; since v15.1.0 multiple Fee Schedules can be created from one (e.g. yearly) Fee Structure, i.e. installment splitting — [Frappe docs: Fee Schedule](https://docs.frappe.io/erpnext/user/manual/en/fee-schedule)
- Fee Schedules generate Sales Invoices (draft by default unless "Submit Sales Invoice from Program Enrollment / Fee Schedule" is enabled); from v15.3.0 Sales Orders can be generated instead — [Frappe docs: Fee Schedule](https://docs.frappe.io/erpnext/user/manual/en/fee-schedule)
- The legacy "Fees" doctype is deprecated from v15.1; old records retained but no new ones; Sales Invoice (one per student per Fee Schedule, one line per Fee Category) replaces it. Creating a Fee Category also creates a linked Item — [Frappe docs: Fees](https://docs.frappe.io/education/fees.md)
- The Fees record carried: Student, Program Enrollment, Program, Academic Term, Academic Year, Due Date, posting date/time, Fee Structure link, fee component rows (Fee Category, Description, Amount), Receivable Account, Income Account, Company, Cost Center; payment via Payment Entry with Mode of Payment — [Frappe docs: Fees](https://docs.frappe.io/education/fees.md)
- Lesson: education fees are modelled as ordinary AR documents (invoice + payment entry) in a general ledger, keyed to Program Enrollment — [Frappe docs: Fees](https://docs.frappe.io/education/fees.md)

**OpenEduCat (admissions)**
- An Admission Register is created per course before enrollment; all admissions for that course fall in that register; register carries fee configuration (fee as a service product), min/max admission counts — [OpenEduCat 19.0 Admission Registers](https://doc.openeducat.org/19.0/applications/enrollment/enrollment-admission-register.html)
- Application fee defaults from the register's product but can be overridden; a due date governs when payment must complete to confirm enrollment — [OpenEduCat registration](https://doc.openeducat.org/19.0/applications/enrollment/enrollment-registration.html)
- Register states are draft-first (Draft -> Confirmed/Open; no applications accepted in Draft) — [OpenEduCat new docs: Create Register](https://newdocs.openeducat.org/admission/create-register/)
- Application model `op.admission` is separate from the Student record, with auto-generated application_number; one doc lists states Draft -> Submitted -> Under Review -> Shortlisted -> Admitted -> Enrolled (+Rejected), another a stage-based flow ending in Enroll which creates the student. Sources conflict on exact state names — [OpenEduCat Admission](https://newdocs.openeducat.org/admission/); [Manage Student Admissions](https://newdocs.openeducat.org/admission/admission-process/)
- Frappe Education describes admissions as covering "enquiry to enrollment" (Student Applicant / Student Admission doctypes), but field-level details were not retrieved — [frappe/education GitHub](https://www.github.com/frappe/education)

**Koha (library)**
- Circulation and fine rules are defined per combination of patron category x item type x library, resolved most-specific-to-least-specific with a mandatory all-default rule — [Koha manual: Circulation](https://koha-community.org/manual/22.05/en/html/circulation.html); [Koha issuingrules schema](https://schema.koha-community.org/19_11/tables/issuingrules.html)
- Rule fields include loan period, max checkouts, fine amount, fine charging interval, grace period, overdue fine cap, `cap_fine_to_replacement_price`, `onshelfholds` — [Koha issuingrules schema](https://schema.koha-community.org/19_11/tables/issuingrules.html); [Hackernoon Koha for schools](https://hackernoon.com/part-6-circulation-and-fines-rules-how-to-install-and-set-up-koha-for-schools-e4cbd39528ed)
- Patron categories hold enrolment duration, age limits, overdue notice flag, hold fee — [Koha manual 16.11 Patrons & Circulation](https://koha-community.org/manual/16.11/html/ch02s03.html)

**PH fee structure practice (assessment inputs)**
- University of the East assessment sheets split tuition into downpayment then installments tied to exam periods ("before midterm", "before final"); cancellation of registration charges a processing fee plus fixed amount before classes, and 5% of the balance after the last installment — [UE SY 2026-2027 Graduate School fee sheet](https://www.ue.edu.ph/mla/wp-content/uploads/2026/02/COLLEGES-MANILA-SY-2026-2027-GRADUATE-SCHOOL.pdf); [UE SY 2025-2026 CAS](https://www.ue.edu.ph/mla/wp-content/uploads/2025/07/COLLEGES-MANILA-SY-2025-2026-COLLEGE-OF-ARTS-SCIENCES.pdf)

- Common PH structure: payment upon enrollment, then monthly or per-exam installments; students may enroll by promissory note on hardship; non-payment may mean no exam, withheld grades, or denial of next-term enrollment (commercial guide, lower authority) — [3D Universal: installments](https://3d-universal.com/en/blogs/how-installment-payments-work-in-philippine-universities.html)

**Faculty load (dependency on sections/subjects)**

**Alumni**

### Inferences
(Module designs below synthesize the cited systems plus standard PH HEI practice; treat as proposed requirements, not sourced facts.)

**Shared core anchors used by all modules**: `persons` (single identity; one person may be applicant, student, employee, alumnus, guardian), `academic_years`, `terms` (semester/trimester/summer) with `term_periods` (prelim, midterm, prefinal/semi-final, finals; each with exam dates and payment due date), `programs`, `curricula`, `year_levels`, `subjects` (lec/lab units, contact hours, `has_lab`, `lab_fee_code`), `sections/class_offerings`, `enrollments` (student x term, status, year level, scholastic status) and `enrollment_subjects` (units, add/drop/withdraw dates). `departments/colleges/campuses` for cost centers.

**Admissions**
- Entities: `inquiries` (lead source, program interest, campaign, owner, status), `admission_cycles` (term, program/campus quotas, open/close dates; ~OpenEduCat register), `applications` (applicant person, cycle, 1st/2nd/3rd program choice, applicant type: freshman/SHS grad, ALS passer, transferee, shiftee, second-degree, cross-enrollee, foreign, returnee; status), `requirement_templates` per applicant type (PSA birth certificate, Form 138/SHS report card, Form 137 / SF10, Good Moral Certificate, Transcript/TOR + Honorable Dismissal for transferees, 2x2 photos, medical, NSO marriage cert where applicable, study permit/ACR-I-Card for foreigners), `application_requirements` (submitted/verified/waived/deferred with deadline, file, verifier), `application_fees` (payment link to cashiering), `exam_sessions` (venue, room, capacity, proctor, date/slot), `exam_bookings`, `exam_results` (subtests, raw/percentile/stanine, composite), `interviews`, `evaluation_scores` (weighted rubric: exam %, GWA %, interview %), `admission_decisions` (admit, waitlist, conditional admit, deny; program offered may differ from choice), `offers` (expiry, reservation fee), `acceptances`, `conversion` -> creates `students` with student number and first `enrollment` shell.
- Rules: requirement completeness gates evaluation but "conditional admission with deferred docs" is common (track deadline and auto-hold on enrollment); quotas per program/campus; exam retake limits; rank-and-cut-off per program; scholarship screening can piggyback on exam score; duplicate-applicant detection (name+birthdate+email); applicant data retention/purge for non-enrollees (Data Privacy Act).
- Edge cases: change of program choice after decision; deferment to next cycle; exam no-show/rescheduling; transferee credit evaluation (hands off to registrar academic core); applicant who is a former student (re-admission vs new); minors needing guardian consent.

**Student accounts / fees**
- Entities: `fee_items` (code, type: tuition-per-unit, lab, misc, other/special, one-time new-student, ID, insurance, graduation, NSTP, thesis, PE, energy/aircon, development; GL revenue account; refundable flag; VAT-exempt flag), `fee_schedules` (versioned; effective academic year; scope by program/year level/campus/student category/applicant type; status draft/approved/locked; approved via board/CHED tuition increase consultation), `fee_schedule_lines` (item, basis: per unit/per lab subject/per subject/flat/per term, rate), `payment_plans` (Full/Cash with discount, Installment: downpayment + N installments keyed to term_periods, Monthly), `assessments` (enrollment x schedule version snapshot -> header totals), `assessment_lines` (computed charges, frozen rates), `discounts` (sibling, early-bird/full-payment, employee dependent, academic, alumni, LGU; stacking & cap rules), `student_ledger_entries` (see Q2), `installment_dues` (due date, amount, exam period, status), `promissory_notes`, `penalties/surcharges`, `refunds`, `statements_of_account`.
- Assessment flow: enrollment advising -> subjects loaded -> assessment computed (units x per-unit rate + lab fees per lab subject + misc per term + new-student one-time) -> discounts/scholarships applied (as credit lines, not reduced rates, for auditability) -> payment plan chosen -> downpayment posted -> enrollment "officially enrolled". Re-assessment on add/drop posts delta charges/credits (never edits the original).
- Rules: tuition per unit is the dominant PH basis; installments per exam period (UE pattern); exam permit requires installment due paid or approved promissory note (subject to RA 11984, see Q3 below in Gaps/Inferences); minimum % before finals (DLSU-D 70% pattern); balance carry-forward to next term blocks enrollment; graduation/TOR requires zero balance.
- Edge cases: cross-enrollees from other schools; overload units; subjects with zero tuition (NSTP partial); free tuition in SUCs/LUCs under RA 10931 (charges posted then offset by government credit to keep per-student cost visible); mid-term fee schedule correction; withdrawals with refund schedule.

**Cashiering**
- Entities: `cashier_sessions` (cashier, window/terminal, opening fund, open/close timestamps), `payments` (payer, student, channel, amount, reference no., status: pending/posted/voided/bounced), `payment_allocations` (to installment dues/fee items by allocation rule e.g. oldest-first or penalties-first), `receipts` (BIR-registered OR/Invoice series, ATP/PTU details, serial range, voided flag with reason), `receipt_series` (per cashier/terminal), `payment_channels` (cash, check, card, bank OTC, online banking, InstaPay/PESONet, GCash, Maya, ShopeePay, aggregator e.g. Dragonpay/ECPay/PayMongo/Xendit, LANDBANK Link.BizPortal), `channel_settlements` (batch import, fees withheld), `daily_collection_reports` (by cashier/session, denomination breakdown), `deposits` (bank deposit slip linkage), `reconciliations` (system vs bank vs aggregator).
- Rules: OR/invoice numbers sequential, never reused; voids require supervisor approval and retain original; cashier session must balance (cash count vs system) with over/short recorded; online payments post via webhook/batch file with idempotent reference matching; unidentified payments go to suspense/unapplied account until matched.

**Scholarships / financial assistance**
- Entities: `scholarship_programs` (internal academic/athletic/cultural/employee-dependent/sibling; external: CHED/UniFAST TES, TDP, CHED Merit, DOST-SEI, LGU, private donors), `coverage_rules` (% or fixed of tuition only / tuition+misc / stipend; caps), `eligibility_rules` (GWA thresholds, no failing grade, min units load, income cap, 4Ps/Listahanan status, residency), `scholarship_applications`, `awards` (per term), `renewals` (auto-evaluated against grades at term end), `disbursements` (to ledger as credit or stipend payout), `grantor_billing` (billing statements to CHED/LGU/sponsor; receivable from grantor, not from student), `sponsors`.
- Rules: no double funding (TES vs TDP exclusion), award cannot exceed assessed charges unless stipend; revocation upon disciplinary case or failing grades; retroactive adjustments post reversals.

**Faculty management / workload**
- Entities: `faculty` (employee link, rank: Instructor I-III, Assistant/Associate Professor I-V, Professor I-VI, University Professor (SUC NBC 461 style) or private HEI ranks; highest degree, PRC license, specializations, employment type full-time/part-time/visiting, tenure status), `load_policies` (regular load units per rank/type, max overload, admin designation deloading units), `load_assignments` (faculty x class offering, units/teaching-load credits, lab multiplier), `designations` (dean, chair, coordinator with deloading), `faculty_availability`, `faculty_evaluations` (student, peer, supervisor, self; instrument, period, weighted score; e.g. QCE/NBC 461 for SUCs), `overload_claims` -> payroll.
- Rules: block assignment conflict checks (time/room), qualifications matching subject (degree/specialization), max preparations, part-timer caps, overload approval by dean/VPAA, small-class rules.

**HR**
- Entities: `employees`, `positions` (plantilla item, salary grade/step for SUCs; job grade for private), `appointments` (type: permanent, probationary, temporary, contractual, casual, COS/JO; effectivity, end date), `employment_history`, `leave_types` (VL, SL, special privilege, maternity 105 days RA 11210, paternity, solo parent, VAWC, special leave for women RA 9710, study leave), `leave_balances`, `leave_requests`, `attendance_logs` (biometrics), `shifts`, `payroll_periods`, `payroll_runs`, `earnings/deductions` (SSS/GSIS, PhilHealth, Pag-IBIG, withholding tax, loans), `payslips`, `201_files` documents.
- Rules: multi-level leave approval; leave credit accrual; teaching vs non-teaching rules (faculty often on "vacation service credits" in SUCs); payroll locked after approval with adjustments in next run.

**Library** (Koha-style)
- Entities: `bib_records` (MARC21/Dublin Core), `items` (barcode, call no., item type, location, status), `patrons` (link to person; category: student, faculty, staff, alumni, external), `circulation_rules` (category x item type x branch), `loans`, `holds`, `fines/fees` (overdue, lost, damage, processing), `library_payments` (or post to student ledger), `clearance_status`.
- Rules: fines with grace period, interval, cap, cap at replacement price; block borrowing above fine threshold; clearance requires no loans + no unpaid fines.

**Alumni**
- Entities: `alumni` (person, degrees, batch, honors), `contact_updates`, `employment_records`, `tracer_surveys` (versioned questionnaire based on CHED GTS), `survey_responses`, `events`, `event_registrations`, `donations/pledges`, `alumni_id_cards`, `chapters`.
- Rules: auto-create on graduation (registrar conferral); tracer cadence (e.g. 1/3/5 years after graduation); consent for directory/publication.

**Student services**
- Clearance: `clearance_types` (term-end/exam, graduation, transfer/honorable dismissal, withdrawal), `clearance_requirements` per office, `holds` raised by any module (library fines, ledger balance, unreturned lab equipment, clinic medical, guidance exit interview, discipline sanction, org/council dues, registrar docs). A clearance is satisfied when no active hold for required offices; manual sign-off optional.
- ID: `id_cards` (validity per term, RFID/QR, lost/replacement fee posts a charge, validation sticker per term).
- Clinic: `health_records` (sensitive personal info), `consultations`, `medical_certificates`, `immunizations`, annual PE/medical clearance.
- Guidance: `counseling_sessions` (confidential, restricted access), `referrals`, `exit_interviews`, psych tests.
- Discipline: `incident_reports`, `cases`, `hearings`, `sanctions` (warning, suspension, exclusion, expulsion; CHED rules require due process), `appeals`; sanctions create holds.

**Portals**: Applicant (apply, upload docs, pay application fee, book exam, see results/offer, accept), Student (enrollment, assessment, SOA, online payment, grades, clearance status, exam permit, schedule, requests), Faculty (load, class lists, grade entry, evaluation results, payslip, leave), Parent/Guardian (see Q3), Alumni (profile update, tracer survey, events, document requests e.g. TOR/diploma copies), Public website (programs, admissions, fees transparency, news, events, inquiry form feeding CRM).

## 2. What accounting rules apply to student ledgers (double-entry, charges vs credits, audit trail, no deletion, reversals)?

### Takeaway
Treat the student account as an AR subledger of a double-entry GL: every assessment, discount, scholarship, payment, penalty, refund and correction is an immutable posted entry with a typed "detail code" (charge vs credit) mapped to GL accounts; corrections are reversals plus re-posting, never edits or deletes. ERPNext implements this with Sales Invoices/Payment Entries against receivable and income accounts per cost center; Banner uses typed detail codes in a single account detail table.

### Cited Findings
- ERPNext Education fees post through Sales Invoices with Receivable Account, Income Account, Company and Cost Center; payments via Payment Entry; submitting updates accounts automatically — [Frappe docs: Fees](https://docs.frappe.io/education/fees.md); [Fee Structure](https://docs.frappe.io/education/fee-structure)
- Invoices are draft by default (not posted) until submitted; i.e. a draft/posted distinction — [Frappe docs: Fee Schedule](https://docs.frappe.io/erpnext/user/manual/en/fee-schedule)
- Banner AR stores receivable detail in TBRACCD; each transaction carries a detail code, and the detail code type determines whether it is a charge or a payment — [Missouri State Banner ODS metadata](https://prodssb.missouristate.edu/metadata/Accounts_Receivable_ODS_index.html); [NEU Receivable Account Detail](https://bnrordsp.neu.edu/metadata_nfs/RECEIVABLE_ACCOUNT_DETAIL_ODS_target.html)
- Banner posts student charges/payments via TSADETL and reviews via TSAAREV — [Foothill-De Anza Banner AR training](https://fhdafiles.fhda.edu/downloads/eisDocs/ARAccountsReceivable80WB.pdf)
- Banner has an "Account Detail Purge" process, so "never deleted" is not an absolute in Banner (conditions unknown) — [Jefferson Banner AR User Guide](https://banadmin.jefferson.edu/Banner_Docs/Banner_Accounts_Receivable_User_Guide.pdf)
- BIR EOPT (RA 11976) and RR 7-2024: the invoice replaced the official receipt as the primary document for sales of services; OR/collection/payment receipts become supplementary proof of payment; remaining ORs could be used until consumed/converted by stamping "Invoice" — [PwC PH EoPT invoicing clarified](https://www.pwc.com/ph/en/tax/tax-publications/taxwise-or-otherwise/2024/eopt-invoicing-clarified.html); [KPMG PH](https://kpmg.com/ph/en/home/insights/2024/07/compliance-an-update-to-registration-procedures-and-invoicing-requirements.html); [Philstar](https://philstar.com/business/2024/06/22/2364566/bir-extends-use-official-receipts-until-fully-consumed)
- RR 11-2025 as amended by RR 26-2025: mandatory e-invoicing/EIS reporting for large taxpayers, e-commerce sellers and users of computerized accounting/invoicing systems, with a 31 Dec 2026 date cited; RMC 98-2026 issued on e-invoice issuance — [KPMG PH Special InTax Sept 2026](https://kpmg.com/ph/en/insights/2026/09/special-intax-september-2026-issue-1-volume-2.html)
- One secondary primer (Aug 2025) claims schools may issue statements of account but must issue an OR upon every tuition payment — single source, unverified — [Respicio: OR requirements](https://www.respicio.ph/commentaries/legal-requirements-for-issuing-official-receipts-in-the-philippines)

### Inferences
- Ledger design: `student_ledger_entries(id, student_id, term_id, posted_at, effective_date, entry_type: CHARGE|CREDIT, detail_code, amount>0, source_type/source_id (assessment, payment, scholarship award, penalty run, refund, adjustment), reverses_entry_id, reason, created_by, approved_by, batch_id, gl_journal_id)`. Balance = sum(charges) - sum(credits), computed, never stored as authoritative (cache allowed).
- Each detail code maps to GL: charge -> Dr Accounts Receivable-Students / Cr Tuition Revenue (or Unearned Tuition if recognized over the term) ; payment -> Dr Cash/Cash-in-Bank/Clearing (e-wallet) / Cr AR ; scholarship (internal) -> Dr Scholarship Expense or contra-revenue (Tuition Discounts) / Cr AR ; government grant -> Dr Receivable from CHED/LGU / Cr AR-Student (moves the receivable to grantor) ; penalty -> Dr AR / Cr Other Income ; refund -> Dr AR (or Refund Payable) / Cr Cash ; overpayment -> credit balance shown as Student Deposits/Refundable liability.
- Immutability: posted entries are append-only; corrections = reversal entry (same amount, opposite type, `reverses_entry_id`) + new correct entry; voided OR keeps number with VOID status. Database-level: no UPDATE/DELETE grants on ledger tables; audit log with actor/IP/timestamp; period close locks a term/month so back-dated postings go to the open period with reference. This mirrors the FinDesk `Ledger::post` balancing pattern.
- Revenue recognition: tuition assessed at enrollment can be credited to Unearned Tuition and amortized monthly over the term (PFRS 15 practice) — verify with institution's auditor.
- Allocation of payments to installment dues: deterministic rule (penalties -> oldest due -> current), recorded in `payment_allocations` so exam-permit eligibility is reproducible.
- Discounts posted as separate credit lines (not reduced rates) to preserve gross revenue reporting and scholarship cost reporting.
- Every receipt/invoice number tied to a BIR-registered series (ATP/PTU, or CAS/CBA permit/registration for computerized systems); e-invoice transmission queue to EIS if the school falls under RR 11-2025 coverage.

## 3. What do parent/guardian portals typically expose and how is consent handled? (Plus PH collections/exam-permit law and refunds)

### Takeaway
Under the PH Data Privacy Act, grades are treated as sensitive information; for students under 18 parental consent is needed, but for adult college students the student's own consent should govern what a parent sees. Design the parent portal as a student-granted, scoped, revocable delegation (grades, schedule, SOA/payments, attendance, clearance), with minors defaulting to guardian access. Separately, RA 11984 (No Permit, No Exam Prohibition Act) constrains "no permit, no exam" holds.

### Cited Findings
- UP Diliman DPO opinion on a parent/guardian grade-notification system: obtain the student's consent; for students under 18 also obtain parent/guardian consent; consent should specify which grades, to whom, and by what method; collect only needed data — [UP DPO Opinion 19-32](https://privacy.upd.edu.ph/wp-content/uploads/2020/05/DPO-Opinion-19-32-ParentGuardian-Notification-System.pdf) (university DPO opinion, not NPC ruling)
- A 2025 legal primer says grades are sensitive personal information and disclosure outside original purpose needs data-subject consent; parents may access grades if the student is a minor — [Respicio: Data Privacy for Student Grades](https://www.respicio.ph/commentaries/data-privacy-for-student-grades-in-the-philippines) (secondary)
- UP student registration consent-form opinion and UP student privacy notice show the practice of consent captured at registration — [UP DPO Opinion 20-14](https://privacy.upd.edu.ph/wp-content/uploads/2022/05/DPO-Opinion-20-14-UP-Diliman-Student-Registration-Consent-Form.pdf); [UP Privacy Notice for Students 2024-2025](https://our.uplb.edu.ph/wp-content/uploads/2024/10/UNIVERSITY-OF-THE-PHILIPPINES-UP-PRIVACY-NOTICE-FOR-STUDENTS-REVISED-AS-OF-THE-1st-SEMESTER-2024-2025.pdf)
- RA 11984 "No Permit, No Exam Prohibition Act" (2024) covers public and private basic, higher education and long-term TVIs: students with unpaid fees may take exams if they present a certificate from the local SWDO or DSWD regional office of disadvantaged status (calamity, emergency, force majeure, other justifiable reasons); schools may voluntarily extend this; schools may still require promissory notes, withhold records/credentials, and pursue other legal remedies; violators face administrative sanctions by DepEd/CHED/TESDA — [Conventus Law summary](https://conventuslaw.com/report/philippines-no-permit-no-exam-prohibition-act/)
- Regino v. Pangasinan Colleges (2004) had recognized "no permit, no exam" as a practice schools may impose — [Conventus Law](https://conventuslaw.com/report/philippines-no-permit-no-exam-prohibition-act/)
- Refunds on withdrawal (CHED MORPHE, CMO 40 s.2008): secondary sources conflict. One: before classes full refund less non-refundable reservation; week 1: 80% tuition; week 2: 50%; week 3: 20%; after: none — [Respicio: withdrawal fees](https://www.respicio.ph/commentaries/are-withdrawal-fees-legal-philippine-rules-on-school-tuition-refunds-after-enrollment); another: 90% week 1 / 80% week 2 — [Respicio: refund delays](https://www.respicio.ph/commentaries/legal-remedies-for-school-tuition-refund-delays-and-consumer-protection); another: school may keep up to 25% for week-1 withdrawal — [Respicio: refund policy violations](https://www.respicio.ph/commentaries/school-tuition-refund-policy-violations-student-legal-rights-in-the-philippines).- UE charges 5% of balance on cancellation after last installment due, a school-level policy example — [UE fee sheet](https://www.ue.edu.ph/mla/wp-content/uploads/2026/02/COLLEGES-MANILA-SY-2026-2027-GRADUATE-SCHOOL.pdf)

### Inferences
- Parent portal exposure (typical): student profile summary, enrollment status and schedule, grades per period (prelim/midterm/final), attendance/tardiness if tracked, SOA and payment history, online payment (parents are usually the payers), installment due reminders, exam permit status, clearance holds, announcements/events, disciplinary notices (minors), clinic visit notifications (minors, limited).
- Consent model: `guardian_links(student, guardian_person, relationship, is_minor_basis, status, verified_by, verified_at)` + `guardian_access_grants(link, scope[] e.g. grades, finance, attendance, discipline, health; granted_by student/guardian/registrar; valid_from/until; revoked_at)`. Rules: if student < 18, guardian link (verified with PSA birth cert/ID) has default scopes; at 18th birthday system prompts student to confirm/revoke; adult student grants scopes explicitly; finance scope can be granted independently (payer access) because sponsors/parents pay; all accesses logged; revocation immediate. Health and guidance records excluded by default.
- Payer-only accounts: a parent or sponsor may pay with student number + reference without seeing grades (pay-by-reference link).
- Exam permit logic must support an RA 11984 override flag (`disadvantaged_certificate` document, issuing SWDO/DSWD, validity term) that allows exam access while the balance remains and records/credentials stay withholdable; promissory note workflow (student request -> accounting/dean approval -> due date -> auto-hold if missed).
- Refund engine should be policy-configurable (date bands x % retained, per fee item refundability), since the national default is uncertain and schools may adopt own policies.

### Gaps
- No NPC Advisory Opinion directly on releasing adult college students' grades to parents was found.
- Primary text of CHED MORPHE refund sections not obtained; percentages conflict across secondary sources. From prior knowledge (unsourced here), the MORPHE rule is often quoted as "withdraw within first week: charged 10% of total fees; within second week: 20%; after second week: full fees" — this conflicts with the secondary sources above and must be verified against CMO 40 s.2008 (Sec. ~99-101).
- RA 11984 IRR (DSWD certificate rules) and exact effectivity date not retrieved.

## 4. What workflow and approval patterns are standard (multi-step approvals, notifications)?

### Takeaway
Standard patterns are state machines with draft -> submitted -> reviewed -> approved/rejected states, role-based approvers per step, and notifications at each transition; the cited systems show draft-first records (OpenEduCat registers/applications, ERPNext draft vs submitted invoices) and payment-request notifications. PH practice adds office-by-office clearance sign-offs and promissory-note approvals.

### Cited Findings
- OpenEduCat admission registers must be confirmed/opened before accepting applications; applications move through Draft -> Submitted -> Under Review -> ... -> Enrolled with Rejected branch (state names vary by version) — [OpenEduCat Admission](https://newdocs.openeducat.org/admission/); [OpenEduCat workflow of registration](https://doc.openeducat.org/19.0/applications/enrollment/enrollment-workflow.html)
- ERPNext invoices created as Draft by default with a setting to auto-submit; Fees had a "Send Payment Request" option to notify the student — [Frappe Fee Schedule](https://docs.frappe.io/erpnext/user/manual/en/fee-schedule); [Frappe Fees](https://docs.frappe.io/education/fees.md)
- Koha uses scheduled jobs for holds queue and hold expiry and patron category flags for overdue notices — [Koha manual circulation](https://koha-community.org/manual/22.05/en/html/circulation.html); [Koha 16.11 Patrons & Circulation](https://koha-community.org/manual/16.11/html/ch02s03.html)
- Online payment posting latency example: MSEUF posts Dragonpay payments to the student portal within one working day of confirmation — [MSEUF Online Payment Guide](https://mseuf.edu.ph/pages/online-payment-guide)
- UE: tuition paid via InstaPay to a PNB account needs no emailed proof, but miscellaneous fees require emailing proof (manual matching) — [UE how to pay](https://www.ue.edu.ph/mla/how-to-pay-ue-tuition/)
- Channels in use at PH HEIs: ECPay School (via GCash Bills, Maya Bills), Dragonpay, LANDBANK portal (GCash, Maya, ShopeePay); UP Manila linked with GCash; some units exclude Maya/InstaPay — [Xendit ECPay School](https://docs.xendit.co/docs/ecpay-school); [MSEUF](https://mseuf.edu.ph/pages/online-payment-guide); [UP Manila GCash](https://www.upm.edu.ph/cpt_news/going-e-upm-links-with-gcash-for-ease-of-payment-transactions/); [UPD Stat graduate payment](https://sites.google.com/up.edu.ph/statgraduate-upd/procedures/payment-of-tuition-fees)
- GCash offers a "Study Now, Pay Later" tuition loan (GGives) — a third-party financing channel paying the school — [GCash help](https://help.gcash.com/hc/en-us/articles/53172962777625-GCash-Study-Now-Pay-Later-Loan-Program)
- UniFAST TES: applications go through the HEI's UniFAST focal person; 2026 Revised TES Guidelines (MC No. 01 s.2026) reported to apply from 1st sem AY 2026-27; TES and TDP overlap excluded for new applicants; amounts conflict (2023 memo Php 20,000/AY; a third-party site cites Php 27,000/semester for some categories) — [UniFAST TES](https://unifast.gov.ph/tes.html); [uni2study TES](https://www.uni2study.com/articles/unifast-tertiary-education-subsidy-tes); [CHED RO2 RM 226 s.2023](https://chedregion2.com/wp-content/uploads/series-of-2023-RM-No.-226.pdf)
- RA 10931 free tuition covers students in their first undergraduate degree in SUCs/LUCs subject to admission and retention policies; TES is a separate grant-in-aid under Sec. 7 — [PhilScholar TES](https://philscholar.com/ched-unifast-tertiary-education-subsidy/); [UniFAST](https://unifast.gov.ph/tes.html)

### Inferences
- Generic workflow engine: `workflow_definitions(entity_type, version)`, `workflow_steps(order, role/assignee rule e.g. dean of student's college, SLA, parallel|sequential)`, `workflow_instances`, `workflow_actions(actor, action approve/reject/return/delegate, comment, timestamp)`; notifications via email/SMS/in-app (Bootstrap toasts per FinDesk pattern) on transitions, due-date reminders (installment due 3 days before each exam period), escalation after SLA.
- Typical approval chains: Admission decision (evaluator -> admissions committee -> director); Discount/scholarship award (scholarship office -> accounting -> VP Finance); Promissory note (student -> accounting/student accounts -> dean or VP Finance for large amounts); Refund (student request -> registrar withdrawal confirmation -> accounting computation -> VP Finance -> cashier/disbursement); OR void (cashier -> chief cashier/controller, same day only); Ledger adjustment (accountant -> controller); Faculty load (chair -> dean -> VPAA), overload (dean -> VPAA -> HR/payroll); Leave (supervisor -> HR -> head for long leave); Clearance (parallel sign-offs by each office, auto-cleared when no holds); Discipline (incident -> discipline officer -> committee hearing -> president for expulsion, with appeal).
- Payment posting: online channels via webhook + daily settlement file reconciliation; unmatched -> suspense queue for cashier review; OTC bank deposits via student-uploaded proof matched by cashier.
- Government grant workflow: generate list of eligible enrolled students -> validate with UniFAST/CHED -> bill grantor -> on remittance post grantor payment and close grantor receivable.

### Gaps
- No primary-source PH university accounting/cashier procedure manual was retrieved (searches surfaced only fee sheets and payment pages).
- Official current TES amounts for AY 2026-27 not confirmed from UniFAST primary docs.

## 5. What open-source systems (OpenEduCat, Fedena, Koha, Frappe/ERPNext Education) model these and what can we learn?

### Takeaway
ERPNext/Frappe Education: fees are just AR on a full GL (Fee Category = Item, Fee Structure template, Fee Schedule per student group -> Sales Invoice/Order, Payment Entry); OpenEduCat: admission register per course/cycle with fee product and applicant model separate from student; Koha: the gold-standard rules matrix (patron category x item type x branch) for circulation and fines. Borrow these patterns rather than inventing; PH-specific features (per-unit tuition, exam-period installments, promissory notes, BIR receipts, RA 11984) must be added on top.

### Cited Findings
- ERPNext moved from a bespoke "Fees" doctype to standard Sales Invoices (v15.1) and optionally Sales Orders (v15.3), and allows multiple fee schedules per structure — showing the trend to reuse core accounting documents — [Frappe Fees](https://docs.frappe.io/education/fees.md); [Fee Schedule](https://docs.frappe.io/erpnext/user/manual/en/fee-schedule)
- Fee Structure requires Student Category, enabling category-based pricing (e.g. scholar vs regular) — [Frappe Fee Structure](https://docs.frappe.io/education/fee-structure)
- OpenEduCat applications are a separate model (`op.admission`) from Student; enrolling creates the student — [OpenEduCat Admission](https://newdocs.openeducat.org/admission/)
- OpenEduCat 18.0 admission module sends instance telemetry (URL, versions, DB UUID, active users) to OpenEduCat servers — privacy consideration — [Odoo apps: openeducat_admission 18.0](https://apps.odoo.com/apps/modules/18.0/openeducat_admission)
- Koha resolves rules most-specific-first with a mandatory default; supports fine caps and replacement-price caps — [Koha manual](https://koha-community.org/manual/22.05/en/html/circulation.html); [ByWater: circ rules](https://bywatersolutions.com/news/circ-rules-koha310)
- Koha prefers computing data as needed rather than duplicating it — [Koha circulation rules (Hackernoon)](https://hackernoon.com/part-6-circulation-and-fines-rules-how-to-install-and-set-up-koha-for-schools-e4cbd39528ed)

### Inferences
- Lessons to adopt: (1) versioned fee schedule templates with scope dimensions and a generic rule resolver (Koha-style most-specific-wins over program x year level x campus x student category); (2) assessments snapshot rates at posting time; (3) applicant entity distinct from student, conversion creates student + carries documents; (4) admission cycle/register controls quotas and fees; (5) reuse the existing GL (`Ledger::post`) rather than a separate fee ledger; (6) Koha integration via patron sync and fines/holds API rather than rebuilding a full ILS (MARC cataloguing is a large domain) — integrate Koha (REST API) or build lightweight circulation if scope demands.
- Things missing in these OSS systems for PH: per-unit tuition with lab-fee per subject, exam-period installment plans and permit logic, promissory notes, BIR receipt series/ATP/CAS compliance, RA 11984 overrides, CHED/UniFAST TES/TDP billing, GCash/Maya/aggregator reconciliation, office-based clearance.

### Gaps
- Fedena's data model (finance categories, fee collections, fee particulars, discounts, fines) was not researched within the tool budget.
- Koha holds/reserves table schema not retrieved.
- PeopleSoft Student Financials item types/payment priority not retrieved.
